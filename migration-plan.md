# План миграции katet.tech с WordPress на headless CMS/CRM

Дата аудита: 25.05.2026

## 2. Важные SEO-наблюдения

- Сайт на WordPress, SEO-разметка генерируется Yoast SEO.
- У всех проверенных индексируемых страниц есть canonical, robots `index, follow` и базовая JSON-LD разметка.
- У статей есть `Article`; у посадочных страниц чаще `CollectionPage`; у карточек техники сейчас в основном `WebPage`, а не полноценный `Product/Offer`.
- В sitemap много URL указано как `http://katet.tech/...`, хотя canonical уже `https://katet.tech/...`. При миграции sitemap нужно отдавать только HTTPS URL.
- В `robots.txt` закрыты WordPress-служебные зоны, параметры, поиск, feed, `reviews/*`, `zapros/*`, `wp-json`. После переезда нужно убрать WP-следы и сохранить запрет параметров/служебных страниц.
- У части архивов и отзывов description пустой. Это зона для улучшения, но менять массово лучше после фиксации текущих позиций и приоритетов.

## 3. Рекомендуемый стек

Основной вариант:

- Frontend: Next.js 15+ с App Router, TypeScript, SSR/SSG/ISR.
- Headless CMS/CRM: Directus выбран как основной вариант для миграции.
- База: PostgreSQL.
- Медиа: S3-совместимое хранилище или локальное хранилище с CDN.
- Поиск по сайту: Meilisearch/Typesense или встроенный индекс PostgreSQL на первом этапе.
- Формы и заявки: отдельный модуль lead management в CMS/CRM + интеграции Telegram/почта/CRM.
- Деплой: VPS/Docker Compose или managed-хостинг. Важно иметь staging-домен.

Решение по CMS: Directus. Для этого сайта он подходит лучше Payload на первом этапе, потому что структура похожа на SEO-каталог с четкими SQL-сущностями, связями, характеристиками, редиректами и заявками. Payload остается возможной альтернативой, если позже понадобится полностью code-first CMS внутри Next.js-стека.

Начальный Directus-контур создан в `directus/`: Docker Compose для Directus/PostgreSQL, SQL-схема контента и импортный скрипт из локальной WordPress-базы.

## 4. Модель данных

Уточнение после доступа к БД WordPress:

- `spetstekhnika` — custom post type: 124 опубликованные карточки техники и 3 pending.
- `brand` — taxonomy: 49 terms.
- `vid-techniki` — taxonomy: 65 terms.
- `tipy-rabot` — taxonomy: 24 terms.
- `zapros` — legacy taxonomy: 2 terms, не переносится как новая CMS-сущность.
- `reviews` — custom post type: 27 опубликованных отзывов.
- `post` — 39 опубликованных статей; `/blog/` в sitemap учитывается отдельно.

Это значит, что посадочные `/brand/...`, `/arenda/...` и `/tipy-rabot/...` нужно импортировать не как обычные страницы, а как SEO-термы с контентом, метаданными и связями к карточкам `spetstekhnika`.

Минимальные коллекции:

- `pages`: статические страницы с блоками, SEO, slug, canonical, robots.
- `equipment_types`: SEO-лендинги `/arenda/...`.
- `equipment_items`: карточки `/arenda_spetstekhniki/...`.
- `work_types`: посадочные `/tipy-rabot/...`.
- `brands`: посадочные `/brand/...`.
- `posts`: блоговые статьи.
- `post_categories`: рубрики блога.
- `reviews`: отзывы и источники отзывов.
- `cities`: городские посадочные, если они есть среди статических страниц.
- `media_assets`: изображения, PDF, документы.
- `redirects`: таблица 301/410 правил.
- `leads`: заявки с форм, звонков, мессенджеров.

Ключевые поля для всех индексируемых сущностей:

- `slug`, `url_path`, `legacy_wp_id`.
- `h1`, `title`, `meta_description`.
- `canonical_url`, `robots`, `lastmod`.
- `breadcrumbs` или связи для генерации хлебных крошек.
- `content_blocks` для повторяемых блоков страницы.
- `schema_type` и JSON-LD override при необходимости.
- `published_at`, `updated_at`, `status`.

Для техники:

- Цена, единица цены, наличие, скидка.
- Характеристики: грузоподъемность, колесная формула, длина стрелы, грузовой момент и др.
- Связи с видом техники, брендом, типами работ, похожими единицами.
- Галерея изображений, alt/title изображений.

## 5. Шаблоны frontend

Нужно повторить текущий дизайн, но собрать его компонентно:

- `GlobalHeader`: желтая верхняя панель, контакты, поиск, WhatsApp/Telegram, основное меню.
- `HeroWithLeadForm`: темный hero с фото техники, бейдж скидки, H1, телефонная форма, согласие, мессенджеры.
- `EquipmentTypePage`: `/arenda/...`, hero, преимущества, список карточек техники, SEO-текст, FAQ/контентные блоки.
- `EquipmentItemPage`: `/arenda_spetstekhniki/...`, белая товарная страница с изображением, характеристиками, преимуществами, ценой, наличием, CTA.
- `WorkTypePage`: `/tipy-rabot/...`, лендинг услуги/работы с привязкой техники.
- `BrandPage`: `/brand/...`, посадочная по марке с подборкой техники и SEO-текстом.
- `BlogIndex` и `PostPage`: блог, статьи, рубрики.
- `ReviewPage` и блок отзывов.
- `CityPage`: городские посадочные, если они должны остаться индексируемыми.
- `StaticPage`: контакты, о компании, доставка и оплата, политика.
- `SearchPage`: только если нужен индексируемый или закрытый от индексации поиск.

## 6. SEO-правила миграции

Главное правило: старые URL должны остаться теми же. Для всех 351 URL из sitemap нужно заранее определить статус:

- `200`: страница переносится один-в-один по тому же path.
- `301`: страница объединяется с другой и получает точный редирект.
- `410`: страница осознанно удаляется, если она не нужна и не имеет трафика/ссылок.
- `noindex`: служебные страницы, если они нужны пользователю, но не должны быть в индексе.

Обязательные SEO-сохранения:

- URL path и trailing slash.
- Title, description, H1.
- Canonical.
- Robots meta.
- Open Graph/Twitter image и описание.
- Хлебные крошки и JSON-LD `BreadcrumbList`.
- Organization/WebSite/SearchAction.
- Article schema для статей.
- Product/Offer или Service schema для карточек техники и услуг, если данные позволяют.
- Alt изображений.
- Внутренние ссылки меню, футера, карточек и хлебных крошек.
- XML sitemap с HTTPS URL, корректным `lastmod` и разбивкой по типам.
- Robots.txt без WordPress-мусора, но с запретом параметров и служебных URL.

## 7. План работ

### Этап 0. Доступы и фиксация baseline

- Получить доступ к WordPress admin, SSH/SFTP, базе данных, `wp-content/uploads`.
- Получить Google Search Console, Яндекс.Вебмастер, Яндекс.Метрику/GA, текущие цели и формы.
- Снять текущие позиции/трафик/страницы входа за 3-12 месяцев.
- Сохранить текущие sitemap, robots, HTML ключевых страниц и список всех индексируемых URL.
- Сделать краул через Screaming Frog/Sitebulb: статусы, title, description, H1, canonical, word count, images, internal links.

### Этап 1. Экспорт WordPress

- Экспортировать posts, pages, custom post types: `spetstekhnika`, `vid-techniki`, `tipy-rabot`, `brand`, `reviews`; `zapros` учитывать только как legacy signal, но не переносить как публичную сущность.
- Экспортировать Yoast SEO meta: `_yoast_wpseo_title`, `_yoast_wpseo_metadesc`, canonical, robots, focus keywords, schema settings.
- Экспортировать Elementor/ACF/кастомные поля, если используются.
- Скопировать media library с сохранением имен файлов и размеров.
- Составить mapping `old_wp_id -> new_entity_id -> final_url`.

### Этап 2. Проектирование CMS

- Создать коллекции и связи из раздела 4.
- Настроить роли: контент-менеджер, SEO, администратор, менеджер заявок.
- Задать обязательность SEO-полей для индексируемых сущностей.
- Сделать preview URL для черновиков.
- Заложить историю изменений и workflow публикации.

### Этап 3. Frontend и дизайн

- Перенести текущую визуальную систему: логотип, желтый верхний бар, меню, hero, фиолетовые CTA, карточки, типографику.
- Сверстать все шаблоны из раздела 5.
- Реализовать адаптивные состояния мобильного меню, форм, карточек и таблиц характеристик.
- Сохранить текущие CTA: звонок, быстрый заказ, Telegram, WhatsApp.
- Подключить формы к новой таблице заявок и уведомлениям.

### Этап 4. Импорт данных

- Написать idempotent импорт из WP export/DB в новую CMS.
- Перенести HTML/контентные блоки с очисткой мусорной WordPress/Elementor-разметки.
- Перенести изображения, PDF и alt-тексты.
- Сохранить `lastmod`, если он важен для sitemap.
- Проверить 100% URL из `katet-url-inventory.csv`.

### Этап 5. SEO QA на staging

- Сравнить старый и новый HTML для всех шаблонов.
- Проверить, что у всех индексируемых страниц ровно один H1.
- Проверить title/description/canonical/robots по всем URL.
- Проверить 301 для измененных URL и отсутствие 302/цепочек.
- Проверить schema.org валидатором.
- Проверить sitemap и robots.
- Проверить Core Web Vitals/PageSpeed на главной, `/arenda/...`, карточке техники, статье, контактах.
- Проверить, что staging закрыт от индексации через basic auth или `noindex`.

### Этап 6. Запуск

- Заморозить контент в WP на время финального экспорта.
- Сделать финальный импорт.
- Прогнать контрольный краул staging.
- Переключить DNS/прокси.
- Проверить 20-30 приоритетных URL вручную и автоматом все URL из sitemap.
- Отправить новые sitemap в Google Search Console и Яндекс.Вебмастер.

### Этап 7. Мониторинг после запуска

- Первые 72 часа: лог 404/500, формы, скорость, индексация, ошибки sitemap.
- Первые 2-4 недели: позиции, клики, страницы входа, crawl stats, новые ошибки в вебмастерах.
- Все найденные 404 с трафиком переводить в 301 или восстанавливать страницу.
- SEO-улучшения запускать после стабилизации, чтобы не смешать эффект миграции и редизайна.

## 8. Что можно улучшить относительно текущего WP

- Сделать карточки техники полноценными SEO-сущностями с `Product/Offer` или `Service` schema.
- Исправить sitemap на HTTPS-only.
- Улучшить пустые meta description у отзывов и архивов.
- Закрыть/редиректнуть авторский архив, если он не приносит ценности.
- Убрать WordPress-служебные следы из robots и HTML.
- Ускорить изображения: AVIF/WebP, responsive sizes, preload hero image.
- Сделать управляемые связи между техникой, брендами, видами работ и городами, чтобы внутренние ссылки генерировались стабильно.

## 9. Что нужно от владельца

- Доступ WordPress admin с правами администратора.
- SSH/SFTP или доступ к панели хостинга.
- Дамп базы данных или доступ phpMyAdmin/Adminer.
- Архив `wp-content/uploads`.
- Доступ к Google Search Console и Яндекс.Вебмастер.
- Доступ к Яндекс.Метрике/GA и целям.
- Список приоритетных страниц/услуг, которые дают заявки.
- Решение по CMS: Directus, Payload или Strapi.
- Где будет хостинг новой версии: текущий сервер, новый VPS, облако.

## 10. Минимальный порядок решений

1. Подтвердить, что все текущие URL должны сохраняться без смены path.
2. Выбрать headless CMS/CRM.
3. Получить доступы и выгрузить WP.
4. Сделать staging с закрытой индексацией.
5. Перенести сначала 1 страницу каждого шаблона и сверить SEO/дизайн.
6. Перенести весь контент.
7. Провести полный SEO QA.
8. Запустить и мониторить 2-4 недели.
