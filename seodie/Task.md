# ТЗ: автоматизированная система генерации SEO-контент-плана на основе Wordstat и контекста компании

## 1. Назначение системы

Разработать систему, которая автоматически формирует SEO-контент-план для сайта компании на основе:

* данных из Wordstat;
* контекста компании;
* текущей структуры сайта;
* существующих страниц;
* поискового спроса;
* географии работы компании;
* продуктовой матрицы;
* аналитики по текущему трафику;
* правил качества и бизнес-приоритетов.

Система не должна требовать ручного составления тем, ключевых слов или контент-плана.

Роль человека — проверять, корректировать и утверждать автоматически предложенные кластеры, страницы и ТЗ.

---

## 2. Главный принцип

Система не получает готовый список тем от человека.

Система получает:

```text
1. Контекст компании
2. Seed-данные из продуктовой матрицы
3. Данные Wordstat
4. Данные текущего сайта
5. Данные аналитики
```

и сама формирует:

```text
1. Список поисковых запросов
2. Кластеры запросов
3. Интенты
4. Приоритеты
5. Рекомендации: создать / обновить / объединить / не делать
6. Черновой контент-план
7. ТЗ на каждую страницу
8. Очередь задач для ревью
```

---

## 3. Что система НЕ должна делать

Система не должна:

* требовать от пользователя ручного списка тем;
* требовать от пользователя ручного списка ключевых слов;
* публиковать страницы без проверки качества;
* создавать страницы только потому, что запрос есть в Wordstat;
* создавать дубли существующих страниц;
* создавать локальные страницы без достаточного основания;
* создавать страницы с одинаковой структурой и заменой одного слова;
* выдумывать услуги, цены, технику, характеристики, районы и кейсы;
* создавать контент-план “из головы” без данных спроса;
* генерировать статьи до прохождения этапа кластеризации и утверждения.

---

## 4.1. Администратор

* утверждать публикации;

Может:

* принимать или отклонять темы;
* объединять кластеры;

* редактировать автоматически созданное ТЗ;
* отправлять ТЗ на генерацию текста;
* отправлять страницу на доработку.

Может:

Может:

* подтверждать факты о компании;

# 6. Источники данных

## 6.1. Контекст компании

Система должна хранить структурированный контекст компании.

Контекст компании включает:

* список услуг;
* категории услуг;
* типы техники или продуктов;
* задачи клиентов;
* зоны работы;
* ограничения;
* преимущества;
* условия заказа;
* минимальные условия оказания услуги;
* сезонность;
* запрещенные темы;
* нерелевантные направления;
* целевые клиенты;
* типовые боли клиентов;
* FAQ;
* кейсы;
* фото;
* текущие страницы сайта.

Важно: контекст компании не является готовым контент-планом. Он используется только как источник seed-данных и фильтр релевантности.

---

## 6.2. Wordstat

Система должна получать из Wordstat:

* поисковые фразы;
* частотность;
* региональность;
* сезонность, если доступна;
* связанные запросы;
* похожие запросы;
* уточняющие запросы;
* вложенные запросы;
* динамику интереса, если доступна.

Подключение к Wordstat должно быть реализовано через отдельный модуль-адаптер.

Адаптер должен поддерживать несколько режимов:

```text
1. Официальный API, если доступ есть.
2. Импорт CSV/XLSX, если выгрузка выполняется вручную.
3. Подключение внешнего парсера, если API недоступен.
4. Импорт из сторонних SEO-инструментов, если они используются.
```

Система не должна быть жестко завязана на один способ получения данных.

---

## 6.3. Текущий сайт

Система должна собирать:

* все URL сайта;
* title;
* description;
* H1;
* H2;
* canonical;
* статус индексации;
* HTTP-статус;
* внутренние ссылки;
* текст страницы;
* тип страницы;
* дату публикации;
* дату обновления;
* наличие формы заявки;
* наличие CTA;
* наличие FAQ;
* наличие schema.org.

---

## 6.4. Аналитика

Желательно подключить:

* Google Search Console;
* Яндекс.Вебмастер;
* Яндекс.Метрику;
* CRM;
* коллтрекинг;
* данные по заявкам;
* данные по звонкам;
* данные по конверсиям.

Эти данные используются не для первичной генерации тем, а для уточнения приоритетов.

```sql
CREATE TABLE wordstat_seed_terms (
    id SERIAL PRIMARY KEY,

    seed_type TEXT,
    region TEXT,
    status TEXT DEFAULT 'active',
```

Seed-терм может быть создан из:

* названия услуги;

* региона;
* связки “услуга + задача”;

* связки “задача + регион”;
* часто задаваемого вопроса;
* формулировок из CRM;
* формулировок из звонков;
* формулировок из текущих страниц сайта.

# 8. Автоматическое создание seed-термов

## 8.1. Назначение

Seed-термы нужны, чтобы система знала, какие направления проверять в Wordstat.

Seed-термы не являются готовыми ключевыми словами для статей. Это стартовые точки для сбора реального спроса.

---

## 8.2. Источники seed-термов

Система должна автоматически генерировать seed-термы из:

```text
company_context.service
company_context.service_category
company_context.equipment_type
company_context.task
company_context.region
company_context.customer_segment
company_context.faq
existing_site_pages
crm_requests
call_transcripts
manager_notes
```

---

## 8.3. Правила генерации seed-термов

Для каждого активного элемента контекста система создает набор seed-вариантов.

Пример логики без конкретных тем:

```text
service_name
service_name + region
service_name + task
service_name + commercial_modifier
task + service_category
task + region
equipment_type + task
equipment_type + region
question_template + service_name
```

---

## 8.4. Фильтры seed-термов

Seed-терм не создается, если:

* направление отключено для SEO;
* услуга не оказывается;
* регион не обслуживается;
* тема находится в списке запрещенных;
* термин слишком общий;
* термин не связан с бизнесом;
* термин относится к нецелевому сегменту;
* термин ведет к нерелевантному спросу.

---

# 9. Сбор данных из Wordstat

## 9.1. Общая логика

Для каждого seed-терма система должна:

1. Отправить запрос в Wordstat.
2. Получить список поисковых фраз.
3. Получить частотность.
4. Получить региональные данные, если доступны.
5. Получить связанные запросы, если доступны.
6. Сохранить сырые данные.
7. Передать данные на очистку.

---

## 9.2. Параметры сбора

Настраиваемые параметры:

```yaml
wordstat:
  regions:
    - "{{primary_region}}"
    - "{{secondary_region}}"
  max_depth: 2
  min_frequency: 5
  include_related_queries: true
  include_nested_queries: true
  include_seasonality: true
  request_limit_per_day: 1000
  retry_on_error: true
  cache_ttl_days: 30
```

---

## 9.3. Частота обновления

Рекомендуемая логика:

```text
Высокоприоритетные seed-термы: 1 раз в неделю
Среднеприоритетные seed-термы: 1 раз в месяц
Низкоприоритетные seed-термы: 1 раз в квартал
Сезонные направления: перед началом сезона
Новые услуги: сразу после добавления в контекст компании
```

---

## 9.4. Кэширование

Система должна кэшировать результаты Wordstat, чтобы:

* не превышать лимиты;
* не собирать одни и те же данные повторно;
* сравнивать динамику спроса;
* строить исторические тренды.

---

# 10. Очистка ключевых слов

## 10.1. Задача

На этом этапе система должна удалить нерелевантные, мусорные и неподходящие запросы.

---

## 10.2. Автоматические фильтры

Запрос исключается, если:

* содержит запрещенную тему;
* относится к неоказываемой услуге;
* относится к нецелевому региону;
* содержит явный информационный мусор;
* содержит бренд конкурента, если стратегия это запрещает;
* относится к покупке, если компания работает только с арендой;
* относится к вакансии, обучению, инструкции для специалистов, если это нецелевой интент;
* содержит признаки бесплатного, пиратского, нерелевантного или некоммерческого спроса;
* не имеет связи с контекстом компании;
* частотность ниже минимального порога;
* является дублем другого запроса.

---

## 10.3. Нормализация

Для каждого запроса система должна определить:

```text
нормализованную фразу
леммы
части речи
гео-модификаторы
коммерческие модификаторы
вопросительные модификаторы
задачные модификаторы
объект работ
тип услуги
тип техники / продукта
интент
```

---

## 10.4. Результат очистки

Каждый запрос получает статус:

```text
relevant
irrelevant
needs_review
duplicate
too_broad
too_narrow
forbidden
out_of_region
not_business_fit
```

---

# 11. Классификация интентов

## 11.1. Задача

Система должна определить, что хочет пользователь, который вводит запрос.

---

## 11.2. Основные типы интентов

```text
commercial_service
commercial_local
commercial_price
commercial_comparison
informational_how_to
informational_selection
informational_cost_estimation
faq
case_or_example
brand
competitor
irrelevant
unknown
```

---

## 11.3. Правила классификации

Интент определяется на основе:

* слов-модификаторов;
* структуры запроса;
* частотности;
* региона;
* связи с услугами;
* связи с задачами;
* выдачи поисковой системы, если SERP-анализ включен;
* текущих страниц сайта;
* исторических данных по конверсиям.

---

## 11.4. Confidence score

Для каждого интента система должна сохранять уверенность:

```json
{
  "intent": "commercial_service",
  "confidence": 87,
  "signals": [
    "commercial_modifier_detected",
    "service_detected",
    "region_detected",
    "matches_company_context"
  ]
}
```

Если confidence ниже заданного порога, запрос отправляется на ручную проверку или не используется для генерации плана.

---

# 12. Кластеризация запросов

## 12.1. Назначение

Система должна объединить запросы в смысловые кластеры, чтобы один кластер соответствовал одной потенциальной странице или одному блоку существующей страницы.

---

## 12.2. Методы кластеризации

Система должна использовать гибридный подход:

```text
1. Лемматизация и совпадение основных сущностей
2. Группировка по услуге / задаче / региону
3. Группировка по интенту
4. Семантическая близость через embeddings
5. Проверка SERP-схожести, если доступна
6. Проверка существующих URL сайта
```

---

## 12.3. Правила кластера

Один кластер должен иметь:

* один основной интент;
* одну главную сущность;
* понятный тип будущей страницы;
* список основных запросов;
* список вторичных запросов;
* список вопросов;
* частотность;
* географию;
* бизнес-релевантность;
* рекомендуемое действие.

---

## 12.4. Когда запросы НЕ объединять

Запросы нельзя объединять, если:

* у них разные коммерческие интенты;
* один запрос требует услуги, другой — статьи;
* один запрос локальный, другой общий;
* один запрос про цену, другой про выбор;
* один запрос относится к разным сегментам клиентов;
* один запрос ведет на существующую страницу, другой требует новую;
* SERP показывает разные типы страниц.

---

## 12.5. Когда запросы нужно объединять

Запросы нужно объединять, если:

* они описывают один и тот же спрос;
* отличаются только словоформой;
* отличаются только порядком слов;
* имеют одинаковый интент;
* должны вести на одну и ту же страницу;
* могут быть раскрыты в одном FAQ-блоке;
* низкочастотные запросы усиливают основную тему.

---

# 13. Проверка текущего сайта

## 13.1. Задача

Перед созданием новой страницы система должна проверить, не закрыт ли уже этот спрос существующей страницей.

---

## 13.2. Site Gap Analyzer

Для каждого кластера система должна проверить:

```text
Есть ли существующий URL под этот интент?
Есть ли страница с похожим H1?
Есть ли страница с похожим title?
Есть ли страница, которая уже получает показы по этим запросам?
Есть ли риск каннибализации?
Можно ли обновить существующую страницу вместо создания новой?
Нужно ли добавить FAQ-блок?
Нужно ли добавить раздел на услугу?
Нужно ли создать отдельную страницу?
```

---

## 13.3. Возможные решения

```text
create_new_page
update_existing_page
merge_with_existing_cluster
add_faq_to_existing_page
add_section_to_existing_page
no_action
manual_review
```

---

# 14. Scoring-модель

## 14.1. Назначение

Система должна ранжировать найденные кластеры не только по частотности, но и по бизнес-ценности.

---

## 14.2. Business Fit Score

Оценка соответствия бизнесу.

```text
0–100 баллов
```

Учитывать:

* услуга действительно оказывается;
* запрос связан с целевым направлением;
* регион входит в зону работы;
* есть подтвержденные данные;
* есть коммерческий потенциал;
* нет юридических или операционных рисков;
* запрос не ведет к нерелевантному клиенту;
* компания может качественно закрыть потребность.

---

## 14.3. SEO Opportunity Score

Оценка SEO-возможности.

```text
0–100 баллов
```

Учитывать:

* суммарную частотность кластера;
* количество запросов в кластере;
* конкуренцию;
* наличие слабых конкурентов в выдаче;
* текущие позиции сайта;
* есть ли уже показы;
* можно ли быстро улучшить существующую страницу;
* сезонность;
* региональность.

---

## 14.4. Content Readiness Score

Оценка готовности данных для создания качественной страницы.

```text
0–100 баллов
```

Учитывать:

* есть ли описание услуги;
* есть ли характеристики;
* есть ли фото;
* есть ли FAQ;
* есть ли кейсы;
* есть ли ограничения;
* есть ли подтвержденные условия;
* есть ли данные для CTA;
* есть ли внутренние ссылки.

---

## 14.5. Risk Score

Оценка риска.

```text
0–100 баллов
```

Учитывать:

* риск дубля;
* риск doorway-страницы;
* риск выдумывания фактов;
* риск нерелевантного трафика;
* риск низкой конверсии;
* риск каннибализации;
* риск слишком тонкой страницы;
* риск публикации без уникальной пользы.

---

## 14.6. Итоговый Content Priority Score

Формула:

```text
Content Priority Score =
Business Fit Score * 0.35
+ SEO Opportunity Score * 0.30
+ Content Readiness Score * 0.25
- Risk Score * 0.10
```

Пороговые значения:

```text
80–100: высокий приоритет
60–79: средний приоритет
40–59: низкий приоритет
0–39: не брать в работу
```

# 15. Генерация контент-плана

## 15.1. Что считается контент-планом

Контент-план — это не список вручную придуманных тем.

Контент-план — это автоматически сформированная очередь `content_plan_items`, где у каждого элемента есть:

* кластер запросов;
* интент;
* рекомендуемый тип страницы;
* рекомендуемое действие;
* приоритет;
* причина попадания в план;
* риски;
* нужные данные;
* целевой URL;
* статус проверки;
* следующий шаг.

---

## 15.2. Поля элемента контент-плана

```json
{
  "cluster_id": 123,
  "page_type": "service | article | faq | local_page | comparison | update | case | hub",
  "recommended_action": "create_new_page",
  "priority": 87,
  "confidence_score": 91,
  "reason": "Высокая бизнес-релевантность, подтвержденный спрос, нет существующей страницы",
  "risk_score": 18,
  "missing_data": [],
  "target_existing_url": null,
  "proposed_url": "/generated-placeholder/",
  "status": "pending_review"
}
```

---

## 15.3. Правила автоматического попадания в план

Кластер попадает в контент-план, если:

```text
Business Fit Score >= 70
SEO Opportunity Score >= 40
Content Readiness Score >= 50
Risk Score <= 50
нет критической каннибализации
есть понятный интент
есть рекомендуемое действие
```

---

## 15.4. Правила исключения из плана

Кластер не попадает в план, если:

```text
услуга не оказывается
регион не обслуживается
интент непонятен
тема запрещена
нет достаточного спроса
нет бизнес-ценности
высокий риск дубля
тема уже закрыта существующей страницей
страница будет слишком тонкой
система не может объяснить, зачем нужна эта страница
```

---

## 15.5. Группировка плана

Система должна группировать план по:

* типу действия;
* приоритету;
* направлению бизнеса;
* региону;
* интенту;
* статусу;
* риску;
* готовности данных.

# 20. Логика recommended_action

## 20.1. create_new_page

Выбирать, если:

```text
есть спрос
есть бизнес-релевантность
нет существующей страницы
нет риска каннибализации
есть достаточно данных
интент требует отдельной страницы
```

---

## 20.2. update_existing_page

Выбирать, если:

```text
есть существующий URL
URL уже получает показы по части запросов
контент слабый или неполный
интент совпадает
создание новой страницы вызовет дубль
```

---

## 20.3. add_faq_to_existing_page

Выбирать, если:

```text
запросы вопросительные
частотность умеренная или низкая
интент связан с существующей услугой
отдельная статья не нужна
ответ можно дать коротким блоком
```

---

## 20.4. add_section_to_existing_page

Выбирать, если:

```text
кластер раскрывает подтему существующей страницы
есть смысл усилить текущий URL
не нужен отдельный материал
```

---

## 20.5. merge_with_existing_cluster

Выбирать, если:

```text
кластер почти совпадает с другим
интент одинаковый
разделение создаст каннибализацию
```

---

## 20.6. no_action

Выбирать, если:

```text
низкий спрос
низкая бизнес-ценность
тема нерелевантна
высокий риск
нет данных
страница уже закрывает спрос
```

# 21. Защита от плохого контент-плана

## 21.1. Анти-doorway правила

Система должна блокировать создание страниц, если:

```text
страница отличается от другой только регионом
нет уникального локального контекста
нет отдельного интента
нет бизнес-обоснования
нет достаточной частотности
нет данных компании по этому направлению
```

---

## 21.2. Анти-дубли

Перед созданием новой страницы проверять:

```text
похожие URL
похожие title
похожие H1
похожие кластеры
похожие интенты
запросы, по которым уже ранжируются существующие страницы
```

---

## 21.3. Анти-мусор

Не добавлять в план кластеры, если:

```text
интент неясный
запросы слишком общие
нет коммерческой связи
нет связи с услугами
нет потенциала заявки
нет возможности дать экспертный ответ
```


# 33. Definition of Done

Система считается готовой на уровне MVP, если:

```text
1. Контекст компании загружается и редактируется.
2. Seed-термы создаются автоматически.
3. Wordstat-данные импортируются или получаются через адаптер.
4. Запросы очищаются и нормализуются.
5. Запросы классифицируются по интенту.
6. Запросы объединяются в кластеры.
7. Каждый кластер получает score.
8. Система проверяет текущий сайт.
9. Система сама формирует content_plan_items.
10. Человек может ревьюить предложения.
11. После approve система создает ТЗ.
12. В ТЗ нет ручных тем, выдуманных ключей и неподтвержденных фактов.
13. Все решения системы имеют объяснение.
14. Отклонения ревьюера сохраняются и влияют на будущие рекомендации.
```

# 34. Ключевой результат

После внедрения человек больше не составляет контент-план вручную.

Процесс должен выглядеть так:

```text
Компания обновляет контекст
→ система сама собирает спрос из Wordstat
→ сама чистит ключи
→ сама группирует запросы
→ сама определяет интенты
→ сама проверяет сайт
→ сама предлагает, что создать или обновить
→ человек утверждает или отклоняет
→ система сама формирует ТЗ
→ контентный пайплайн создает материал
```

Главная ценность системы:

```text
Контент-план рождается из реального поискового спроса и бизнес-контекста,
а не из ручного списка тем или догадок SEO-специалиста.
```
